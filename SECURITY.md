# Security

## Scope

Socksicle is a desktop proxy client for Windows and Linux.

Security-sensitive parts of the project include:

* local storage of proxy credentials and subscription URLs
* proxy engine configuration
* TUN mode
* kill switch firewall rules
* subscription fetching
* TwinSock encrypted storage and share tokens

## Threat model

Socksicle's local encryption is designed primarily to protect sensitive configuration data stored on disk.

It is intended to provide protection against:

* casual inspection of configuration files
* accidentally exposing passwords, UUIDs or keys through plain-text JSON
* moving encrypted configuration files to another machine
* tampering with encrypted values

It is **not** intended to protect against a fully compromised operating system, malware running as the same user, or an attacker who can freely execute code inside the user's session.

## Local encrypted storage

Sensitive fields in Socksicle configuration files are stored as opaque `tws3.*` tokens instead of plain-text values.

The current TwinSock v3 implementation uses:

* AES-256-GCM for authenticated encryption
* HKDF-SHA256 for key derivation
* randomly generated nonces for encrypted values
* machine-specific identifiers for local vault key derivation

On supported systems the vault derives its machine identity primarily from:

* Windows `MachineGuid`
* Linux `/etc/machine-id`

Additional system properties are included in the fingerprint.

Because the vault is machine-bound, copying the configuration to another machine is expected to prevent the encrypted values from being unlocked there.

### What this protects

An attacker who only obtains files such as:

```text
servers.json
subscriptions.json
drawer.json
```

should not be able to read protected credentials directly from the stored ciphertext.

### What this does not protect

Local encryption does not protect secrets while Socksicle is actively running.

A process with sufficient access to the user's session may be able to:

* inspect application memory
* read decrypted configuration through the running process
* intercept traffic generated by the application
* modify or replace the application itself

Machine binding also does not replace full-disk encryption or operating-system access controls.

## TwinSock share links

Socksicle can create `tws3://` share tokens for transferring encrypted configuration data.

Share tokens use AES-256-GCM and are derived from a user-provided share key.

Unlike the local vault, share tokens are intentionally **not machine-bound**, so they can be transferred between devices.

Anyone who obtains both a share token and the corresponding share key may be able to decrypt the protected contents.

Treat share keys and share tokens as secrets.

## Legacy TwinSock v2

Socksicle retains read support for legacy `tws2` data for backward compatibility.

Legacy v2 data uses the previous cryptographic format and is treated as deprecated.

New data is written using TwinSock v3.

Users should migrate legacy configuration data to v3 where possible.

## TUN mode

TUN mode uses `sing-box` to route system traffic through a virtual network interface.

Privilege requirements vary by platform.

On Linux, Socksicle can use Polkit and Linux capabilities for the operations required to create and manage the TUN interface instead of running the entire GUI as root.

TUN mode should be considered an operating-system networking feature rather than a cryptographic privacy guarantee.

## Kill switch

The optional kill switch uses operating-system firewall rules to block direct outbound traffic when the protected tunnel is unavailable.

Supported implementations currently use:

* Windows `netsh advfirewall`
* Linux `nftables` where available

The kill switch is designed to reduce the chance of traffic leaving the system outside the configured tunnel.

It should not be treated as a guarantee against every possible network leak.

Changes to the operating system, firewall configuration, routing, kernel networking, third-party software or future Socksicle releases may affect its behavior.

Users should test the kill switch in their own environment before relying on it for sensitive traffic.

## Subscription URLs

Subscription URLs are fetched by Socksicle and may contain credentials or other sensitive information.

For this reason:

* HTTPS should be preferred over HTTP
* subscription URLs should not be shared publicly
* subscription providers can observe requests made to their endpoints
* configured User-Agent and optional `X-hwid` values may be sent to subscription servers

Socksicle rejects subscription URLs that directly resolve to common private, loopback or link-local IP addresses.

This check is a defense-in-depth measure and should not be considered a complete SSRF protection mechanism.

## Proxy engines

Socksicle relies on external proxy engines such as:

* shadowsocks-rust (`sslocal`)
* Xray-core
* sing-box

These engines are separate projects with their own security models and release processes.

Socksicle does not independently reimplement the underlying proxy protocols when an external engine is used.

Users should keep the selected engine version up to date and obtain binaries from trusted sources.

## Reporting a vulnerability

Please do not publicly disclose an unpatched security vulnerability through a GitHub issue.

For security-sensitive reports, provide:

* a description of the vulnerability
* affected versions
* reproduction steps or a minimal proof of concept
* the potential security impact
* any relevant logs or configuration details that do not contain secrets

The report will be reviewed and handled before public disclosure where practical.

## Security limitations

Socksicle should not be considered secure against a compromised host.

In particular, the application does not attempt to defend against:

* kernel-level malware
* a malicious administrator or root user
* code injection into the running application
* arbitrary local process memory inspection
* a compromised proxy server
* malicious or compromised subscription providers
* vulnerabilities in third-party proxy engines or operating-system networking components

Security features in Socksicle are intended as layers of protection rather than guarantees of complete anonymity or confidentiality.

## Dependencies

Socksicle depends on third-party libraries and external engines.

Security issues in dependencies may affect Socksicle even when the Socksicle source code itself is unchanged.

Dependency updates should therefore be evaluated as part of normal maintenance.
